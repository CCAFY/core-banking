# 설계 질문지

영역별로 팀이 정해야 하는 것들. 답은 적혀 있지 않다.
각 영역의 담당자가 대안을 조사해서 ADR 초안을 올리고, 팀이 합의한 뒤 구현한다.

진행 순서: **질문에 답하기 → ADR 작성 → 실패하는 테스트 작성 → 구현**

## 1. 원장 모델 (테이블)

모든 거래가 이 결정에 의존하므로 가장 먼저, 전원이 같이 정한다.

- 계좌의 현재 잔액을 어디에 둘 것인가? 계좌 행에 저장하는 방법, 거래 기록에서 매번 계산하는 방법,
  둘 다 두는 방법이 있다. 각각 조회 속도와 정합성 위험은 어떻게 다른가?
- 거래 한 건을 몇 개의 행으로 기록할 것인가? 이체처럼 계좌 두 개가 걸리는 거래는 어떻게 담는가?
- 복식부기의 차변과 대변을 테이블로 어떻게 표현할 것인가?
- 고객이 맡긴 예금은 은행 입장에서 자산인가 부채인가? 입금 한 건의 차변과 대변은 각각 무엇인가?
- "추가만 가능"을 어디서 강제할 것인가? 애플리케이션 규칙, DB 권한, 트리거를 비교한다.
- 금액, 계좌번호, 날짜 컬럼의 타입과 제약은 무엇인가?
- 증명: 어떤 조회를 돌리면 "장부가 맞다"를 확인할 수 있는가?

## 2. 동시성

- 두 요청이 같은 계좌에 동시에 입금하면, 아무 대책이 없을 때 무슨 일이 생기는가?
  먼저 대책 없이 구현해서 깨지는 모습을 테스트로 재현한다 (`RunInChildren` 사용).
- 대책 후보: 행 잠금(비관적), 버전 컬럼(낙관적), 계산을 SQL 한 문장에 넣기, 격리 수준 올리기.
  각각 "거래 후 잔액을 기록한다", "잔액 부족을 검사한다"는 요구와 잘 맞는가?
- 선택한 방식에서 실패(충돌, 대기 시간 초과)가 나면 호출한 쪽에 무엇을 돌려주는가?
- 증명: 프로세스 N개가 M건씩 넣은 뒤 잔액과 건수가 정확히 맞는가? 대책을 빼면 테스트가 깨지는가?

## 3. 멱등성 (같은 요청이 여러 번 올 때)

- 응답을 못 받은 쪽이 같은 요청을 다시 보내면 어떻게 되어야 하는가?
- 요청을 구분하는 키는 누가 만들고, 어디에 저장하고, 무엇으로 중복을 막는가?
- 중복 요청에는 무엇을 돌려주는가? 오류인가, 처음 처리한 결과인가?
- 같은 키인데 내용(계좌, 금액)이 다르면?
- 같은 키의 요청 두 개가 정확히 동시에 들어오면?
- 증명: 같은 요청을 순서대로 두 번, 그리고 여러 프로세스에서 동시에 보냈을 때 한 번만 반영되는가?

## 4. 출금

- 잔액 부족은 어디서 판단하는가? C 코드, DB 제약, 둘 다 중에서 고른다.
  둘 다 둔다면 두 판단이 어긋날 수 있는 경우가 있는가?
- 잔액 확인과 차감 사이에 다른 거래가 끼어들 수 있는가?
- 출금의 차변과 대변은 무엇인가?
- 증명: 잔액 10,000원인 계좌에 7,000원 출금 두 건이 동시에 들어오면?

## 5. 이체

- 출금과 입금을 한 트랜잭션으로 묶는가? 중간에 실패하면 어떤 상태가 남는가?
- A→B 이체와 B→A 이체가 동시에 들어오면 무슨 일이 생기는가? 먼저 재현한 뒤 해결한다.
- 자기 계좌로 보내는 이체는 허용하는가?
- 이체 한 건의 분개는 몇 줄이고 각각 무엇인가?
- 증명: 여러 계좌 사이에 무작위 이체를 동시에 많이 돌린 뒤 전체 잔액 합계가 그대로인가?

## 6. 취소 (역분개)

- 원거래를 지우지 않고 되돌리려면 무엇을 새로 기록해야 하는가?
- 원거래와 취소 거래를 어떻게 연결하는가?
- 이미 취소된 거래를 또 취소하려고 하면? 취소 거래를 취소할 수 있는가?
- 입금을 취소하려는데 그 돈이 이미 출금됐다면?
- 영업일이 지난 거래도 취소할 수 있는가?
- 증명: 거래 후 취소하면 잔액과 장부가 거래 전과 같은 값으로 돌아오는가?

## 7. 영업일, 일마감, 대사

- 거래일자의 기준은 무엇인가? 영업일은 누가 언제 넘기는가?
- 일마감에서 무엇을 확인하고 무엇을 기록하는가?
- 마감 처리 중에 들어온 거래는 어느 날짜의 거래인가?
- 대사는 무엇과 무엇을 맞춰 보는가? 불일치가 나오면 어떻게 알리는가?
- 증명: 일부러 장부를 어긋나게 만든 뒤 대사가 그 계좌를 정확히 찾아내는가?

## 8. 결과 코드와 함수 규칙

여러 사람이 거래 함수를 나눠 짜기 전에 먼저 맞춘다.

- 결과 코드를 어떻게 나눌 것인가? 정상, 업무 오류(잔액 부족 등), 시스템 오류(DB 장애)를 구분한다.
- 거래 함수의 인자와 반환값 모양을 통일한다. 결과 값(거래 후 잔액 등)은 어떻게 돌려주는가?
- 오류 처리 패턴을 하나로 정한다. C에는 예외도 자동 롤백도 없다 (`src/db.pgc`의 `ledger_db_ping` 참고).
- 입력 검증은 어디까지 C에서 하고 어디부터 DB 제약에 맡기는가?
